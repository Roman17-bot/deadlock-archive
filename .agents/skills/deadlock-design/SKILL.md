# Deadlock visual design

Keep visual complexity proportionate to the page. Tables, item search/catalogue and calculators prioritize loading speed, data readiness and input response. Without an explicit user request for a heavier presentation, prefer existing CSS/SVG and restrained motion; do not add large textures, new renderers, perpetual effects or animation libraries as routine polish. A heavier proposal needs a concrete benefit, scoped loading boundary and measured cost; do not integrate it without the user's direction. Lack of spectacle is not a quality failure.

Locate the active Deadlock checkout; outside it, use the installed deadlock-project locator. Recover project/team context with the existing CLIs rather than importing the chat. Read `docs/design-brief.md`, `docs/design-system.md` and the assigned designer context. The selected Heritage green/ivory/gold direction is the default. Routine design decisions are delegated.

Develop one existing product, not a new independent site for each task. Heritage, approved fonts, architecture and reusable components are the foundation; do not reopen those choices each time. For existing pages, preserve relative placement, order, navigation, data density and interaction meaning. For new pages, use [page workflow](references/page-workflow.md): create a distinct composition within the established product shell without redesigning neighbouring pages. Build on the noir/1930–40s city direction and orange/green/purple shop semantics. Small typography/spacing refinements are allowed within existing areas; relocation needs a separate explicit scope.

Inspect supplied pages/screenshots and current CSS before proposing changes. If no rendered target is available, mark the proposal provisional. Use available project-local `frontend-design` for typography/composition; read `ui-ux-pro-max` only for a specific unresolved UX question. For shader work use available `shader-dev` and [creative graphics](references/creative-graphics.md). Do not load every skill or change the React/CSS stack to fit examples from one.

Choose art direction tied to the page's player task and explain its distinctive craft through composition, lettering, graphics, material or interaction, beyond palette and ornament. Consistent style does not justify copying the same composition on every page. Deliver only the token/type/state specification and assets needed for the assigned surface. See [asset workflow](references/assets.md) for graphics, [creative graphics](references/creative-graphics.md) for Canvas/WebGL/3D, and `docs/design/CREATIVE_DIRECTION.md` for the iteration handoff.

For custom animation, use [motion workflow](references/motion.md). Create working CSS/SVG/Web Animations API or React/TSX examples, with triggers, timing, interruption and reduced-motion behavior. Supply usable source and integration points, not just an animation prompt. The website role or coordinator connects accepted animation to the existing UI.

Write only in assigned locations. Source assets and runnable prototypes belong in the private run; website/coordinator integrate production. For assigned browser work, use the available project Playwright/DevTools MCP bindings described in `docs/design/TOOLS_AND_SKILLS.md`; keep existing computer-use as a fallback. Significant pages/sections require actual 1440/768/390 px self-checks when available, including affected shared components on representative existing pages. Record unavailable checks. Hand off concrete files, layout anchors, actual browser checks and material blockers to a fresh designcritic. Iterate against confirmed findings locally and preserve successful craft; cosmetic churn is not evidence of improvement. Review grants neither publication permission nor new tool access.

Preserve real numbers, RU/EN, private research boundaries and the user's current authorization. No game launch. Keep large source artwork and iteration history private; promote only reviewed optimized assets.
